# MP-040 — Localhost historical REST API (synthetic-only)

The MP-040 HTTP API reads the persisted MP-012 SQLite **synthetic feature snapshots**, motor telemetry and original fixed-rule alerts. It is read-only and creates no new data or simulated ticks. The standard demo remains localhost-only; start with the opt-in database flag to enable history.

    python -m motorpulse --paused --database ./motorpulse-local.sqlite3

The server still binds to 127.0.0.1. With no --database flag, all history endpoints return HTTP **409** and a JSON history_unavailable error, while existing live status, configuration, snapshots and controls retain their previous behavior.

## Endpoints

| Method | Path | Data returned | Supported query fields |
| --- | --- | --- | --- |
| GET | /api/history/sessions | Persisted simulation sessions, stored seed/scenario config and start reason | limit, before_id |
| GET | /api/history/snapshots | Full original versioned snapshot JSON per tick | limit, before_id, session_id, start_utc, end_utc |
| GET | /api/history/events | Original per-motor synthetic telemetry event JSON | limit, before_id, session_id, asset_id, start_utc, end_utc |
| GET | /api/history/alerts | Original synthetic rule warning/critical events and reasons | limit, before_id, session_id, asset_id, start_utc, end_utc |

Example requests (line wraps are explanatory):

    GET /api/history/events?asset_id=MTR-01&limit=20
    GET /api/history/alerts?session_id=<uuid>&limit=10
    GET /api/history/snapshots?start_utc=2026-01-01T00%3A00%3A00Z&end_utc=2026-01-01T00%3A01%3A00Z

Replace the example session UUID placeholder with an actual session ID from GET /api/status or /api/history/sessions. For timestamps using a +00:00 suffix, percent-encode the plus sign as %2B; Z is also accepted. Filters start_utc and end_utc are **inclusive**, refer to **virtual acquisition timestamps**, not session creation wall time, and are interpreted as explicit RFC3339 **UTC seconds with optional 1–6 fractional digits**. Offsets other than UTC are rejected. Storage compares exact integer microseconds, including simulation steps with subsecond offsets; no rounding to seconds or milliseconds.

### Response shape

All successful history responses have HTTP 200, Content-Type application/json, Cache-Control no-store and X-Content-Type-Options nosniff, and this envelope:

    {
      "api_version": "1.0.0",
      "source": "synthetic",
      "resource": "events",
      "items": [
        {"id": 3, "session_id": "<uuid>", "event": {"event_id": "sim:42:MTR-03:1"}}
      ],
      "page": {
        "limit": 50,
        "count": 1,
        "has_more": false,
        "next_before_id": null,
        "order": "id_desc"
      },
      "filters": {}
    }

The abbreviated event shown above is illustrative **only**; actual responses include the complete original telemetry event, with all sensor values, units, scenario and quality annotations. Snapshots return items with id, session_id and snapshot; alerts return id, session_id, asset_id, event_id, tick, timestamp_utc, severity, reasons and source=synthetic_rule. Session items include a numeric id for paging plus the session UUID, creation timestamp, seed, scenario config, start clock, step interval and reason.

Page size limit is a decimal integer from 1 through 100, default 50. History is always **newest first** by increasing SQLite row ID (represented as id_desc). For a page with has_more=true, take next_before_id and pass it back **with the exact same filters** as before_id to read the next, older page. The cursor is an exclusive positive 64-bit row ID and is **specific to its resource**, not a timestamp or a global event offset. Changes from a new simulation tick, restart or reset cannot reorder older rows; it is safe to page while new rows appear. has_more=false means the filtered list is exhausted and next_before_id=null. Empty lists return items=[] with count=0.

All SQL uses bound parameters, including the filters. The timestamps and sensor information are originally generated by the simulator, not a real field acquisition pipeline. Missing/outlier sensor events remain queryable, but only good-sensor rule warning/critical events are stored in /alerts. Repeated active rules produce one record per alerting tick; acknowledgement/deduplication is **not** yet supported (MP-042). The offline trained anomaly model is not integrated into the live alerts API.

### Error contract

| HTTP | Machine code | When |
| --- | --- | --- |
| 400 | invalid_history_query | Unknown or duplicated query field; empty value, invalid UTF-8/percent encoding, page/cursor limits, invalid/reversed/non-UTC time range |
| 409 | history_unavailable | Persistence not enabled; restart using --database |
| 503 | history_storage_error | SQLite read failed or database is unavailable; never return internal SQL messages or filesystem paths |
| 404 | existing unknown API error | No matching /api/history route |

Errors are JSON objects with error (human-readable) and code (stable machine identifier for MP-040 errors). Invalid query requests are rejected before database reads or simulator mutation. No CORS allow-origin header is emitted; no authentication is included because the server is **local-only** and not intended for remote access. Do not port-forward or expose this demo on an untrusted network.

Historical sessions are per-process startup, reset or configuration replacement: intentionally distinct UUIDs even when a simulation tick and original event ID repeat. A restart preserves old sessions but does **not** resume the prior simulator tick. Full histories are not retention-managed, backup-managed or encrypted by the app; protect the local SQLite file and use OS-level backups when needed. MP-013 will add accessible time/motor charts; MP-042 adds alert lifecycle, and MP-043 expands wider API input/error hardening.

## Test and reproducibility

    python -m unittest discover -s tests -p 'test_history_api.py' -v
    python -m unittest discover -s tests -v

MP-040 tests use ephemeral loopback-only HTTP servers and locally created temporary SQLite databases. They exercise the four endpoint envelopes, full original JSON event round-trip, source and motor filters, microsecond UTC boundary behavior, page stability as new data arrive, malformed/duplicate query rejection, SQL parameterization, sensor alert gating, disabled/unavailable database error codes, concurrency and restart history. No external services, actual NASA IMS data, hardware, field reliability claims or extra dependencies are needed.
