# Physical training approval request packet (MP-064)

MP-064 creates a deterministic, source-bound request for a human decision about one exact physical-data training experiment. It consumes an MP-063 preregistration and revalidates the complete MP-062/061/059/060/058 source chain before emitting a metadata-only request packet.

The packet is **not an approval**. Creating it, saving it, validating it, or displaying its challenge phrase never authorizes training.

## Required upstream state

MP-064 accepts only an MP-063 preregistration whose state is exactly:

```text
eligible_for_explicit_training_approval
```

and whose blocker list is empty. A blocked preregistration cannot produce an approval request. The exact preregistration, bundle, readiness assessment, split plan, run cards, evidence reviews, feature files, and protocol are revalidated before the request is built.

A later byte change to any audited MP-058 feature file therefore invalidates the source chain and the request.

## Requested capability

The only capability MP-064 may request is:

```text
offline_training_only
```

The request is restricted to the exact preregistered `standardized_distance_baseline_v1` experiment and exactly these operations:

- fit preprocessing on the `train` partition;
- fit the candidate model on the `train` partition;
- derive the preregistered threshold on the `train` partition.

Validation remains `review_only_no_fit`, and `test_role = final_only_no_fit`. The request does not include validation/test fitting, validation/test threshold selection, model scoring, diagnosis, RUL, deployment, publication, or operational control.

Editing the request JSON cannot broaden those operations because validation recomputes the complete packet from the exact MP-063 preregistration and upstream sources.

## Pending state only

Every valid MP-064 packet has:

```text
approval_state = pending_explicit_human_approval
training_authorized = false
model_scoring_authorized = false
diagnosis_authorized = false
rul_authorized = false
redistribution_cleared = false
```

MP-064 has no state transition to `approved`. It does not accept an approver name, approval timestamp, signature, or decision field, and it exposes no API or CLI action that converts the request into authorization.

A separate later milestone must record a human decision and bind that decision to one exact MP-064 request. Until that separate record exists and passes its own review, training remains unauthorized.

## Approval challenge

Each request receives a deterministic request ID and SHA-256 challenge derived from the exact preregistration, bundle binding, capability, and requested operations. The packet also displays an exact challenge phrase of the form:

```text
APPROVE OFFLINE TRAINING REQUEST physical-training-request:<id> CHALLENGE <sha256>
```

This phrase is a **challenge to be affirmed later by a human**, not an approval generated by the application. Its purpose is to make a future explicit decision unambiguous: a person can quote the exact phrase for the exact request they intend to authorize. Merely generating, copying, storing, logging, testing, or displaying the phrase has no authorization effect.

If any bound source or requested scope changes, a different request/challenge must be generated and any decision about the older request cannot apply to the new one.

## Metadata-only artifact

The request contains only IDs, hashes, the frozen experiment/model identity, requested operations, partition roles, challenge data, pending state, and authorization boundaries. It contains no raw acceleration waveform, no extracted physical feature values, and no local filesystem paths.

## CLI

```bash
python -m motorpulse.physical_training_approval_request \
  --preregistration physical-experiment-preregistration.json \
  --bundle physical-experiment-bundle.json \
  --readiness physical-readiness.json \
  --split physical-split.json \
  --card run-a.json --card run-b.json --card run-c.json \
  --review review-a.json --review review-b.json --review review-c.json \
  --feature features-a.jsonl --feature features-b.jsonl --feature features-c.jsonl \
  --protocol physical-experiment-protocol.json \
  --out physical-training-approval-request.json
```

The output is write-once. Reusing the same output path is rejected rather than overwriting prior evidence.

## What MP-064 does not do

MP-064 **does not train a model**. It does not fit preprocessing statistics, calculate a threshold, score a physical record, diagnose a machine, estimate failure probability, estimate RUL, publish physical measurements, or make a maintenance decision.

It opens no serial port, creates no Wi-Fi/network listener, adds **no PLC** or actuator/control path, and adds no remote deployment capability.

**MP-016 remains ON HOLD** for live sensors, edge/device transport, PLC integration, and remote deployment. A future physical trainer, if explicitly authorized, must remain offline and confined to the exact reviewed experiment scope until separate deployment/security/machine-safety work is approved.
